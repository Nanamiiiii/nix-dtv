# Why Nix?
> [!NOTE]
> そもそもNixとは？という方は [こちら](https://zenn.dev/asa1984/books/nix-introduction) を読むことをオススメします．

TS抜きチューナーによるDTV受信環境はドライバに始まり，チューナーソフトウェアやEPGソフトウェアなど，様々なソフトウェアを連携させて構成する必要があります．
また，各種ソフトウェアは（大人の事情で）ソース配布のみの場合も多く，ビルド環境の整備から入るケースも珍しくありません．

昨今ではDockerコンテナで公開されているケースが多く，とりあえず動かすところまでは容易にできるようになりました．
提供してくださっている有志の方々には感謝しかありません．
しかしながら，設定の複雑さに由来する乱立や再現性といった課題は未だ残ります．

そこでNixの出番です．NixOSに統合することで，パッケージのビルドから各ソフトウェアのConfigurationとその連携まで統一して制御することが可能になります．また，全てが宣言的に記述されるので，マシン初期化時や移行時における環境の再現性も担保できます．

Dockerは非常に優秀で，使用環境の差異による面倒な依存関係の問題を大方解決してくれます．
しかしながら，Dockerも結局は内部で使用するディストリビューションのパッケージマネージャに依存しており，その上流の動きに左右されてしまいます．
これが，古いDockerイメージをビルドできないといった現象が起きる理由の1つです．
また，比較的軽量とはいえ仮想化レイヤーを経由することによる弊害から逃れることも出来ません．

ここでもNixの特徴が生きることになります．
Nixのパッケージビルドでは，ディストリビューションのシステムパッケージのようなものへの暗黙的な依存が存在しません．
ビルド自体も基本的には隔離されたサンドボックスで行われるため，必要な依存パッケージはすべて明示的に宣言されている必要があります．
さらに，Flakesによって依存関係が固定されることで，古いパッケージがビルドできなくなるという可能性もほぼ無くなります．

本モジュールは，Nixの特性を生かしてより容易で，再現性のあるDTV受信環境の構築を目的としています．

現在，上流のnixpkgsにはMirakurunやEPGStationのNix packageとNixOS moduleが取り込まれていますが，更新が滞っている状態です．
